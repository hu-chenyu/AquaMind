# ADR 0006：以 typer 实现命令行入口

- **日期**：2026-09-26
- **状态**：已接受（Accepted，M1 定稿后不再更换）
- **关联**：技术栈选型（见开发计划）、`docs/PROJECT-PLAN.md` 任务 M1-D12
- **决策者**：hu-chenyu

---

## 【决策】我们选了什么

**AquaMind 的命令行入口使用 typer 实现，命令层级为 `aquamind <子命令> <参数>`。**

typer 的核心吸引力在于它把类型标注当作唯一事实来源：一个函数签名同时定义了参数的类型、默认值、是否必需，以及 `--help` 里显示的帮助文本。我们只需要写普通的 Python 函数，不需要再维护一份与之平行、容易与之不同步的参数声明表。对一个 API 表面会随着里程碑快速扩张的项目来说，这种"单一来源"能持续省下维护成本。

它的第二个价值是协作友好。自动生成的帮助信息、清晰的必填/选填标注、以及自然的错误信息，决定了使用者在第一次接触时能否自助解决问题。命令行往往是产品的第一印象，这部分体验值得用库来保证，而不是手写。

第三个理由是它对本项目形态的契合：typer 与 pydantic 同出一源的设计哲学，都与"数据在边界处被严格定义"这条主线一致（见 ADR 0004）。参数校验不必另写一套规则，交给类型系统即可。

需要说明的是，本决策约束的只是**命令行这一层的外壳**。命令背后的执行逻辑属于引擎层与报告层，不会被绑定到 typer 上。

## 【备选】放弃了什么，为什么

### 备选 A：click

**放弃。** click 是 typer 的底层基础，成熟、稳定、社区庞大，也是很多知名工具的选择。它的问题在于抽象层级更低——参数需要显式声明装饰器，参数数量增长后函数签名会变得冗长，帮助文本需要单独编写与维护。

这些都不是致命缺陷，但会持续消耗注意力：我们的场景会有大量可选参数（并发度、预算上限、缓存开关、报告格式、输出路径……），用 click 时它们会变成一长串装饰器堆叠。既然 typer 在底层就是 click，使用它相当于免费获得同样稳定性的同时甩掉样板代码，这个取舍是清晰的。

### 备选 B：标准库 argparse

**放弃。** argparse 的优势是零依赖，在任何环境下的可移植性都最好，这一点确实有价值。但它的表达方式非常命令式：需要逐条注册参数、手工指定类型、手工拼帮助文本和示例。

更重要的是它与类型标注完全脱节。Python 3.5 之后类型标注已经成为表达契约的主流方式，argparse 仍旧要求我们把同样的信息用另一种语法重写一遍。对一个已经决定全量使用类型标注（mypy strict）的项目来说，引入一层不支持类型的命令式配置层是不协调的。

### 备选 C：fire 或类似"约定优于配置"方案

**放弃。** fire 让任何 Python 对象都能立刻变成命令行，上手成本几乎为零，这在写内部一次性脚本时非常高效。但它放弃的正是我们需要的东西：可控性。

对外发布的命令行工具必须精确控制参数顺序、默认值、缩写、帮助文本措辞与错误提示，因为这些都是使用者看到的产品表面。把控制权交给自动约定，意味着我们无法保证这些细节的稳定，也无法在版本演进中维持向后兼容。

## 【边界】什么条件下这个决策失效，届时怎么办

**触发条件一：CLI 复杂度超出 typer 的舒适区。** typer 擅长的是"参数 + 子命令"的形态。如果需要高度定制的帮助输出排布、复杂的命令别名体系、动态生成的选项、或深度定制的补全脚本，typer 的抽象就可能开始碍事而不是帮忙。届时退路是**迁移到 click**——由于 typer 本身构建于 click 之上，这条迁移路径是现成的、成本可控的，不必推倒重来。

**触发条件二：需要极度精简的依赖。** 命令行层的依赖会进入所有使用者的安装体积。若将来出现必须把运行时依赖压到最小的情况（例如作为基底被嵌入某个受限环境），退路是把 CLI 剥离为可选特性组，核心库不依赖 typer，仅在安装 extras 后提供命令行。这条退路的前提是现在就保持命令逻辑与执行逻辑分离。

**触发条件三：交付形态发生根本变化。** 若将来需要的是交互式终端界面（TTY UI）而非一次性命令，那么命令行框架的取舍应当整体重新评估。届时正确的顺序是先修订 ADR 0001（形态决策），再复审本决策——形态决策的优先级高于工具选型。

**额外约束**：本决策明确 M1 定稿后不再更换 CLI 框架。此后的任何更换都必须在维护期执行，并遵循技术栈冻结条款——目的是杜绝由框架替换引发的无收益重构。

**复审时点**：M1 结束时做一次一次性定稿确认；此后每个里程碑只在 checklist 中确认"未变更"，不再重新论证。
