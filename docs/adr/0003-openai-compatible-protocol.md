# ADR 0003：以 OpenAI 兼容接口作为唯一硬承诺协议

- **日期**：2026-09-26
- **状态**：已接受（Accepted）
- **关联**：技术栈选型（见开发计划）、`docs/ROADMAP.md` M1-D05/M1-D11
- **决策者**：hu-chenyu

---

## 【决策】我们选了什么

**AquaMind 在被测对象接入上只做一项硬承诺：支持 OpenAI 兼容接口。除此之外的一切形态，都通过用户自行扩展的适配器接入，不在承诺范围内。**

所谓"硬承诺"，含义是这条路径会被完整实现、持续测试、长期维护，并且在每个版本都保证可用。"硬"的另一面是"唯一"——我们只承诺这一个，其余都不承诺，而不是模糊地说"支持多种协议"。

选择它的现实依据是：这套接口已经成为事实上的行业通用方言。绝大多数模型服务商、企业内网网关以及本地推理服务都会提供一个兼容它的端点。这意味着用一个实现就能覆盖绝大部分实际使用场景，每新增一个被测对象，使用者的边际成本几乎只有改一行配置。

这条决策同时也是一条**范围约束**。它把接入层的工作量封顶：无论外界出现多少种新协议，接入层的常态为一也不需要持续膨胀。省下来的工程量可以投入数据契约、指标定义、报告这些真正与"质量评估"相关的部分。

---

## 【备选】放弃了什么，为什么

### 备选 A：各家私有协议逐个适配

**放弃。** 这个方案的覆盖面理论上最大，但它是典型的无底洞。不同的服务体系在字段命名、流式切分语义、工具调用结构、错误码体系上的差异非常大，且都在持续演进。每适配一家，就等于绑定了一份需要长期跟随、随时可能变化的外部契约。

对单人维护的项目来说，这意味着维护面会随着新增support对象线性膨胀，而其中绝大部分投入无法转化为核心能力。更糟的是，一旦某个协议发生了变化而我们没有及时发现，使用者会以为是我们的 bug。不做逐个适配，是主动控制**不可控的外部依赖数量**。

### 备选 B：完全不承诺任何协议

**放弃。** 这个方案最省事，但等于把全部接入成本推给使用者。LLM 质量评估的第一步就是"把被测对象接进来"，如果这一步需要使用者自己阅读我们的内部接口、自己写适配代码，绝大多数潜在使用者会在第一步流失。

而且它还会导致接入质量失控：每个人写的适配器完整度不同，后续的超时、重试、限流、成本统计都依赖统一的调用边界。没有统一入口，这些横切能力就无处挂载。承诺一个具体协议，本质上是在提供一个稳定的、所有人都踩得来的起点。

### 备选 C：抽象自己的中立协议并要求使用者转换

**放弃。** 表面看最"优雅"，但实质上只是把转换成本从一个地方挪到另一个地方，还额外增加了一层概念负担。使用者需要先理解我们的中立模型、再写转换函数，学习成本高于直接用一个他们已经熟悉的方言。

中立协议真正有价值的场景是协议数量多且长期共存，而当前恰恰相反：事实标准正在向 OpenAI 兼容收敛。在这种背景下自建中立层，是在用一个通用方案解决一个正在自然消失的问题。

## 【边界】什么条件下这个决策失效，届时怎么办

**触发条件一：某种非兼容协议的市场占比高到无法回避。** 如果某天出现一种被广泛采用、但明确不提供兼容层的主流协议，且忽略它意味着放弃一大片使用者，那么"唯一硬承诺"就需要放宽。届时退路是：保持核心抽象不变，由使用者通过 Callable 或通用 HTTP 适配器自建接入，并且**不把它吸收为内置协议**——即扩大"外部生态支持的覆盖范围"，而不扩大"我们自己维护的承诺范围"。两者的成本模型完全不同。

**触发条件二：某种协议的专属语义成为评测的必需能力。** 例如某个协议提供了多模态、原生工具编排或特殊的结构化输出能力，而这些能力无法在兼容接口上表达，导致某些评测指标无法实现。届时退路是在**指标层**而非**接入层**做扩展：允许特定指标声明它需要更丰富的协议能力，并以可选依赖的形式提供专用适配器，主路径保持不变。

**触发条件三：兼容方言本身出现严重碎片化。** 现实中各家的"兼容"程度并不一致，可能存在字段缺失或语义偏移。应对方式是在适配层做**能力协商与降级**——检测到某些能力不可用时明确降级或报错，而不是假装它可用或为每种偏差写补丁。若碎片化严重到"兼容"名存实亡，则应复审本决策。

**复审时点**：M7 收口阶段复审一次；此外每当出现新的主流协议且在半年内稳定占据显著份额时，应及时复审而非等到固定时点。
