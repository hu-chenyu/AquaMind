# ADR 0010：不把 SSE 帧解析器抽为独立包发布

- **日期**：2026-10-11
- **状态**：已接受（Accepted）
- **provenance**：决策日 2026-10-11；三关预检执行于 2026-10-10（外部证据可查，见下文预检 C 的 changelog 原文与 PyPI metadata）
- **关联**：P6-1 外部验证路径 2、`src/aquamind/sse.py`、`scripts/pre_release_scan.py`、ADR 0001（库形态而非平台）
- **决策者**：hu-chenyu

---

## 【决策】我们选了什么

**不把 `sse.py` 抽为独立的零依赖 SSE 解析包发布到 PyPI（放弃 P6-1 路径 2）。该解析器继续作为 AquaMind 内部模块维护，随主包分发，不单独对外承诺 API 稳定性。**

这是一条**负面决策**。写下它的目的不是记录"我们做了什么"，而是记录"我们在什么证据下决定不做什么"——否则半年后重看，会误以为这个模块从一开始就该独立成包。

---

## 【背景】当时的动机

`src/aquamind/sse.py` 是 M1 最深的模块之一：572 行、14 个定义（全部带 docstring）、47 条边界用例、100% 分支覆盖率。基于此产生了"它够深，值得独立成包"的判断（P6-1 路径 2，计划名 `aquamind-sse`）。

在决策前做了**三关预检**，三关全过才发包。结论是：**前两关通过，第三关不通过**——且第三关是否决性的。

---

## 【预检】三关证据

### 预检 A：httpx 依赖深度 —— 通过

剥离 `httpx` 依赖的可行性核查：

| 项 | 实测 |
|---|---|
| 唯一运行时依赖 | `src/aquamind/sse.py:31` 的 `import httpx`，全文仅此一处 |
| httpx 属性访问 | 仅两处，均在类型标注位置：L405 `iter_stream_deltas(response: httpx.Response)`、L472 `collect_stream_content(response: httpx.Response)` |
| 注解是否惰性求值 | 是。文件 L26 有 `from __future__ import annotations`，标注在运行时不求值 |

**结论：剥离成本约 10 分钟**（删 L31 import + 把 L405 / L472 的 `httpx.Response` 标注移入 `if TYPE_CHECKING:` 块下，保留完整类型信息而非退化成 `Any`；文件 L26 的 `from __future__ import annotations` 已使标注在运行时不求值）。技术上可行。

### 预检 B：`.exceptions` 耦合面 —— 通过

| 项 | 实测 |
|---|---|
| 依赖的异常符号 | 仅 `AdapterError` 一个 |
| 其余包内依赖 | 无。`sse.py` 不引用 models / config / budget / replay |
| `AdapterError` 自身规模 | `src/aquamind/exceptions.py` L88-L95，共 8 行，只有类声明与 docstring，无逻辑 |
| `AdapterError` 在 sse.py 的引用面 | **全文约 21 处引用，其中 9 处是真实 `raise`**（L106 / L119 / L214 / L296 / L324 / L432 / L525 / L535 / L549），其余为 docstring 与类型标注 |

**耦合形态单一，抽取成本低。** 三条技术路线：

| 路线 | 做法 | 代价 |
|---|---|---|
| ① 复制异常类 | 在包内重建 `AdapterError` | **高**——必须连同基类 `AquaMindError` 一起复制：它带 `__init__(message, context)` 与两条**防信息泄露**的方法（`__str__` 与 `__repr__` 均只渲染 context 的键名、不渲染取值，见 exceptions.py L35-L52 / L54-L62）。漏抄任一条，异常一旦进入 logging 或异常聚合器就会把响应体、完整 URL 之类的取值带出去——这是一条已修复过的泄露通道，不是普通样板 |
| ② 定义本地 `SSEDecodeError` | 包内自成一套异常 | 中——语义分裂。届时生态里会并存 `AquaMindError` / `AdapterError` / `SSEDecodeError` 三种错误口径，跨包捕获时需要用户自己判断该捕哪一种，得在包 README 里显式声明这层语义差异 |
| ③ 提升为独立小模块 | 把 `AquaMindError` + `AdapterError` 一并移入 `aquamind_sse/errors.py` | 低——纯物理移动，两条防泄露属性跟着走，不存在漏抄 |

**显式选择路线 ③（提升为独立小模块）。** 理由是另外两条都在"安全属性靠人记得抄"或"错误语义分裂"上留了口子，而路线 ③ 把这两个口子都关掉，且改动量最小。

### 预检 C：与 httpx-sse 的正面对比 —— 不通过（否决理由）

对照对象：**httpx-sse 0.4.3**（2025-10-10 发布，Florimond Manca，MIT，PyPI 官方 metadata 核对）。

已覆盖的能力（`connect_sse` / `aconnect_sse` 官方文档原文口径）：

- `connect_sse` / `aconnect_sse` 上下文管理器，`EventSource.iter_sse()` / `.aiter_sse()` 迭代事件；
- `ServerSentEvent` 暴露 `event` / `data` / `id` / `retry` 四个字段，并提供 `.json()`；
- 按 SSE 规范自动设置 `Cache-Control: no-store` 与 `Accept: text/event-stream`；
- 响应 `Content-Type` 不是 `text/event-stream` 时抛 `SSEError`；
- `Last-Event-ID` 与重连间隔（`sse.id` / `sse.retry`）的重连语义，文档给出与 `stamina` 配合的完整示例。

**关键否证**——本项目原本把"行尾解析容错"当作核心卖点，但 httpx-sse 的 changelog 显示该问题早已修复：

```
## 0.4.2 - 2025-10-07
### Fixed
* Fix incorrect newline parsing that was not compliant with SSE spec. (Pull #37)

## 0.4.3 - 2025-10-10
### Fixed
* Fix performance issue introduced by the improved line parsing from release 0.4.2. (Pull #40)
```

即：AquaMind 准备当作差异化卖点的行尾解析问题，竞品在**约一年前**（2025-10-07）已按 SSE 规范修复，随后又在 0.4.3 修掉了该修复引入的性能回退。

剩余的真实增量确实存在——断帧容错、`_MAX_DATA_LENGTH`（1,000,000）与 `_MAX_BUFFER_SIZE`（2,000,000）缓冲上限、非法 UTF-8 不泄裸异常——但这三点**不足以支撑一个独立包**：

1. 它们是**防御性边界处理**，不是能力差异；
2. 更关键的是**"zero-dep" 定位自相矛盾**：httpx-sse 本身依赖 httpx（`requires_dist: httpx`），而本项目 `sse.py` 的 httpx 使用点虽可剥离（L405/L472 仅在标注位置），但剥离后就与 AquaMind 自己的 `iter_stream_deltas` / `collect_stream_content` 消费方割裂——那些函数的存在前提就是"有一个真实在跑的 httpx 响应流"。

## 【备选】放弃了什么，为什么

### 备选 A：抽为独立包 `aquamind-sse` 发布

**放弃。** 三条理由：

1. **这个生态位的需求已被满足。** 需要 SSE 解析器的人，要么已经在用 httpx-sse（主流选择），要么用各家的 SDK；需要 AquaMind 这份解析器的人，已经在用 AquaMind 主包了。独立包的收益来源是"独立用户数"，而这个生态位上该数字不存在。
2. **预期结果可预判为 0 下载。** 本项目当前 PyPI 下载量为 pypistats 实测：月 454 / 周 28 / **日 0**（2026-10 查询）。日归零而月有量的形态与镜像与自动化流量一致；此为形态推断，未逐条核对来源构成。发出去大概率只是多一个无人使用的包。
3. **发布一个自己都不主推的包会消耗维护带宽。** 独立包意味着独立的版本号、独立的兼容承诺、独立的 issue 区。单人维护的项目里，这是明确的负收益。

### 备选 B：保留路径但不叫"zero-dep"，改成"更严格的边界容错"重新包装

**放弃。** 这是在为一个已存在的生态位做差异化包装，投入产出比不足以覆盖发布与维护成本，且需要持续对抗竞品的功能追赶。

### 备选 C：什么都不做，也不写 ADR

**放弃。** "从来没考虑过"与"考虑过并基于证据否决"在可复现性上完全不同。没有 ADR，半年后重新评估时无法知道当初否掉的依据是否仍然成立，会重复调研；也无法向外部说明为什么 AquaMind 的 SSE 实现不承诺独立稳定性。

放弃路径 2 不等于放弃外部验证。保留两条：

| 路径 | 内容 | 时点 |
|---|---|---|

## 【替代动作】放弃抽包之后，这三件事仍值得做

本 ADR 只否决"抽独立包"这一个动作，不否决由此产生的全部工作。以下三项与抽包与否无关，且成本都不高：

**① 回馈上游：把未覆盖的边界用例整理成 issue/PR 提给 httpx-sse。** 本项目 47 条边界用例中，httpx-sse 未覆盖的约 10%（断帧容错、缓冲上限、无尾空行残留、非法 UTF-8 不泄裸异常）是真实增量。把它们整理成可复现的 issue 提给上游，价值有三层：给生态补上真实缺口；建立真实的外部足迹（当前 **PRML（Pre-Registered ML Manifest Specification，预注册哈希兼容规范）** 与 httpx-sse 的作者都是单人维护，开源生态的反馈密度很低）；反哺本 ADR 的故事线——「我们不仅用过它，还研究过它的边界」。

**已排期**：M2 末（10-30/31）或 M3 头 D33 机动，**半天时间盒，超时即止**。执行方式为**先 issue 后 PR**（最小复现 + 差异说明 + 47 用例背景），**不预设被合并**；未被合并同样作为外部足迹证据记入本节。

**执行前的必做核验（20 分钟）**：逐项实测候选缺口是否真为上游缺失。特别注意「2xx 响应流内的 `event: error` 帧」——httpx-sse 的 `ServerSentEvent` 暴露 `.event` 字段，该类帧**很可能已被正确透传**，不自动抛错属于正确的设计选择（库无法知道宿主应用如何定义 error 语义）。若实测确认已透传，则将其从缺失清单移出，作为**设计差异**记录在本节，不提 PR。只对实测确认为缺失的行为提 issue/PR，每项附独立复现与测试。

**② 把预检 C 的对比结论直接用作技术文素材。** 本节的对比过程（AquaMind 剩余增量 vs httpx-sse 已覆盖能力 vs changelog 里那两条修复）已经是可直接引用的成稿，不需要重新组织语言。技术文写"你看到的质量变化有多少是真的"时，可以用它作为「做工程判断」的例子。

**③ 记录方向性判断：若未来做「LLM 流式质量探针」，再重新评估抽包。** 本次否决的前提是「SSE 解析本身没有独立生态位」。如果产品方向变成向外部署一个**流式质量采集探针**——即用户需要在自己的生产环境里持续观测流式质量——那么"独立分发一个可单独安装的探针"就有了真实需求，与本次评估的对象（一个通用 SSE 解析库）不是同一件事。届时应重新做三关预检，而不是直接引用本 ADR 的结论。

## 【边界】什么条件下这个决策失效，届时怎么办

**触发条件一：出现 AquaMind 之外的、真实的第三方 SSE 解析需求。** 判定标准不是"有人在 issue 里问"，而是"有人已经在用并且提了可复现的 bug/PR"。届时的退路是：先在主包内提供该能力，等需求稳定到第二个下游项目，再评估抽包——且抽包后必须重新评估依赖策略（届时可能仍需保留 httpx，因为消费方场景本就如此）。

**触发条件二：httpx-sse 停止维护或出现致命缺口。** 它当前声明为 beta（官方 README 建议锁定 `httpx-sse=="0.4.*"`），且维护者是单一作者。届时的退路是：AquaMind 的解析器可以顺位承接，但**先做迁移成本评估，不要以"竞品没了"作为抽包的充分理由**——生态位消失和需求出现是两件事。

**触发条件三：AquaMind 主包体积或依赖树成为用户实际抱怨点。** 届时的优先解法是 `sse.py` 改为可选 extra（`aquamind[sse]`），而不是拆包——拆包解决不了"主包太大但用户只想要一半"的问题。

**复审时点**：v1.0 发布后（M6 收口 / 维护期首月）复审一次，评估 httpx-sse 的生态变化与 AquaMind 自身的用户需求结构。

## 【教训】这次预检暴露的三个通病

1. **不能凭"这个模块写得深"判断它有独立生态位。** 代码质量与生态位是两个独立维度：前者回答"写得好不好"，后者回答"有没有人会为它单独来一次"。预检 C 之所以通过，是把它当**竞品**查了，而不是当**产品**查了。
2. **"zero-dep" 这类定位词必须与实际依赖一致，否则自相矛盾。** 一个依赖 httpx 的包宣称 zero-dep，会在第一次被人检查依赖时崩塌。
3. **负面决策留痕比什么都不写更有价值。** "我做了三关预检后决定不做"是可以被复核、可以被推翻、也可以在未来条件变化时重新评估的结论；"我做了个重复轮子"则什么都没有。
