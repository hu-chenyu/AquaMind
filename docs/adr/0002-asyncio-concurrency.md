# ADR 0002：评估执行以 asyncio 单线程事件循环为主

- **日期**：2026-09-26
- **状态**：已接受（Accepted）
- **关联**：技术栈选型（见开发计划）、`docs/PROJECT-PLAN.md` asyncio 并发控制（M3-D04）与 VCR 时序回放（M1-D06a~c）
- **决策者**：hu-chenyu

---

## 【决策】我们选了什么

**AquaMind 的执行编排以 asyncio 单线程事件循环为主：批量评测在一个事件循环内并发发起，不做多线程或多进程拆分。**

这个选择的依据来自负载性质。一次评测的绝大部分时间花在等待上——等被测对象的响应、等裁判模型的响应、等限流窗口恢复。这类等待不消耗 CPU，属于典型的 IO 密集型负载，正是事件循环模型最擅长的场景。用一个线程挂起成百上千个协程，上下文切换成本几乎为零，而并发度、超时、重试、限流都可以集中在编排层一处控制和观测。

它同时也降低了复杂度下限。单线程模型下不存在共享内存的竞态问题，不需要考虑锁，大多数数据结构可以直接用普通对象，出问题时的调度路径也可以预测。对一个需要长期单人维护的项目来说，可预测性本身就是一种收益。

需要强调的是"以……为主"而非"全部"。这条决策约束的是**主干编排层**，它不排斥在局部使用其他并发模型来隔离不适用的场景，具体的处理方式写在下面的边界条款里。

---

## 【备选】放弃了什么，为什么

### 备选 A：多线程

**放弃。** Python 的多线程受 GIL 约束，虽然 IO 等待期间会释放锁、表面上和 asyncio 收益接近，但它的开销模型要差很多。每个线程都要付出内存与调度成本，线程数一旦上升到几百，光是线程本身的切换与内存占用就足以吃掉并发带来的收益，实际上限远低于协程。

更麻烦的是正确性负担。多线程意味着所有共享状态都要考虑可见性与竞态，评测过程中要统计失败数、累计成本、汇总指标，这些都是会被并发写入的共享状态。为了维护同一份逻辑，需要额外引入锁或使用线程安全容器，复杂度显著上升而收益为零。

### 备选 B：多进程

**放弃。** 多进程确实绕开了 GIL 的限制，但它解决的是 CPU 密集型问题，而本项目的瓶颈在等待网络，用不上这份能力。代价却是实打实的：进程启动开销、结果需要跨进程序列化回传、子进程崩溃的隔离与恢复策略、以及 Windows 平台下多进程的额外限制。

这些复杂度换来的收益接近于零，属于典型的用复杂方案解决不存在的问题。如果未来确实出现了 CPU 密集型的计算环节，正确的做法也只是在那个局部引入进程池，而不是把主干换成多进程。

### 备选 C：同步串行

**放弃。** 同步串行是唯一真正简单的模型，不需要任何并发设施，调试也最容易。但它在本项目里根本不可用：一次评测往往涉及几十到上百个用例，每个用例又要额外调用裁判模型，串行执行意味着总耗时等于所有单次耗时之和。

具体到体验上，串行跑一批用例可能要几十分钟到数小时，这个数字会让"随手写一次评测"变成一件需要专门安排时间的事，直接摧毁本项目"轻量、随手可用"的定位。因此它可以作为调试模式存在，但不能作为默认模型。

---

## 【边界】什么条件下这个决策失效，届时怎么办

**触发条件一：第三方适配器只提供同步实现。** 评测过程中会接入各类被测对象，其中一部分 SDK 可能只有同步接口且无法替换。若直接在事件循环里调用它们，会阻塞整个循环、把并发度打回 1，反而比串行更糟。届时退路是把这类调用包进线程池执行器（`asyncio.to_thread` 或 `run_in_executor`）做隔离，让它们占用独立线程而不污染事件循环，并在适配器文档中明确标注"该适配器为阻塞型"。

**触发条件二：阻塞调用的数量成为主体。** 如果适配器的形态发生变化——比如绝大多数被测对象都无法以异步方式调用——那么"IO 密集但可异步"这一前提就不再成立，继续坚持事件循环只是在增加一层无意义的封装。届时应当**复盘本决策本身**，而不是继续打补丁；评估方向是退回线程池模型，同时保留统一的抽象接口，让上层编排代码不受影响。

**触发条件三：出现真正 CPU 密集的计算环节。** 比如在本地做大规模文本相似度计算或语料预处理，这类工作会长时间占用 CPU 并饿死事件循环。届时退路是在该环节局部引入进程池或移出到独立步骤，而不是在主干编排层引入多进程。

**复审时点**：M7 收口阶段随性能与成本优化任务（T7-07）复审一次，确认上述三条是否已被触发。
