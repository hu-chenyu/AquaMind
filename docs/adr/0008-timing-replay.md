# ADR 0008：时序保真回放采用同步生成器 + 绝对时刻对齐 + 可测偏差

- **日期**：2026-10-06
- **状态**：已接受（Accepted）
- **关联**：M1-D06a/b/c（VCR 文本 + 时序录制回放）、ADR 0002（asyncio 并发）
- **决策者**：hu-chenyu

---

## 【决策】我们选了什么

**时序调度回放（`play_timed`）采用「同步生成器逐片 yield + 按绝对时刻对齐 sleep + 偏差统计挂在流对象上」的形态：`play()` 与 `play_timed()` 并存为两个独立入口，`speed` 只做「间隔 ÷ speed」的线性折算，无时序可调度时退化为与 `play()` 完全一致的瞬时回放。**

这条决策要解决的是 M1-D06b 留下的半截事：chunk 的到达时刻已经录进 cassette 了，但回放仍然一次性给全。对一个流式测试工具来说，「内容对」只是及格线——打字机效果、进度条推进、首字延迟感受，全都落在**节奏**上；节奏回放不了，这些依赖时序的用例就只能靠真实调用来验，成本与不稳定性都不可接受。

### 决策一：生成器，而不是回调函数

`play_timed()` 返回一个**文本迭代器**，逐片产出 chunk，调用方按普通 `for` 循环消费。

理由是控制流的所有权。流式回放本质上是一条**有节奏的消费链**：调用方拿到第一片就渲染第一片，边渲染边等下一片。用回调表达同一条链，调用方就得反过来——先注册一个 `on_chunk`，再想办法从回调外部的共享状态里判断「开始/结束/异常」。更麻烦的是，回调里的异常会顺着 `time.sleep` 一路冒到调度器内部，调用方拿不到一个可捕获的边界。

生成器把这件事变回 Python 最熟悉的样子：产出节奏由消费速度自然牵引（调用方不消费就不会推进），异常在 `for` 语句所在的那一层抛出，`break` 提前退出就是提前退出。每个 `next()` 都恰好是一次「等到了下一片」的语义，与流式使用方的心智模型完全对齐。

### 决策二：两个入口并存，而不是给 `play()` 挂 `timed` 开关

`play()` 一次性还原完整响应（读取面与 `httpx.Response` 对齐）；`play_timed()` 按时序逐片产出（行为面）。两者并存，不互相替代。

`play()` 是**拿数据**，`play_timed()` 是**复现节奏**，二者服务的下游是不同的一类代码：前者给断言与判分，后者给流式 UI 与 TTFT 相关的用例。合成一个带开关的入口看起来更省事，但会让「这次回放要不要时序」变成一个可以被漏传的参数默认值——同一次回放在不同调用点悄悄给出不同的 chunk 边界，而 chunk 边界正是流式使用方唯一关心的事。分成两个入口，调用点就必须表态，表态本身即文档。

### 决策三：绝对时刻对齐，而不是逐片 sleep 间隔

调度不是「睡完第 1 片的间隔，再睡第 2 片的间隔」，而是以开始时刻为基准算出**每一片的目标时刻**，每片只 sleep「目标时刻 − 当前时刻」的差额。

这两种写法在顺利时结果相同，在不顺利时结果差一个数量级：逐片 sleep 间隔下，第 20 片的实际时刻偏差等于前 19 片偏差之和。一次 15ms 的调度抖动（抢占、GC、CI 机器负载）会被整段流放大到尾部漂移；而使用方对流末端的感知恰恰最敏锐——那正是「输出已经停了几秒却还没结束」的位置。绝对对齐把每片的误差约束在单次定时器精度内，实测 12 片三档倍率的最大偏差都在 1ms 以内（见 `scripts/replay_baseline.json`），且**实测总耗时与计划总跨度之比稳定在 1.00 附近**，说明没有累积漂移。

### 决策四：偏差测量挂在流对象上，用属性读

`TimingDeviation` 不是回调参数，也不是返回值，而是流对象的一个属性（`stream.deviation`），随迭代推进逐步填满。

偏差的定义是「实际到达时刻 − 计划到达时刻」，其中**计划到达时刻已经先除过 `speed`**。这一点决定了指标有没有意义：加速回放时计划时刻同样前移，于是偏差衡量的是「调度本身准不准」，而不是「和原速差多少」——后者只是倍率的定义，不是回放的缺陷。若拿未折算的 `arrival_ms` 当基准，加速回放会凭空显示出一整段等于 `1/speed` 的「偏差」，把一次正确的调度报成一次错误。

汇总指标（最大/平均偏差）取**带符号偏差的绝对值**：回放的目的是复现节奏，「提前 20ms」与「滞后 20ms」对使用者的体感是对称的。需要看方向时读逐片的 `deviations_ms`。

### 决策五：非法倍率显式报错，无时序退化为瞬时回放

`speed <= 0`、NaN、±inf 一律抛 `ReplayError`，**不静默回退成原速**。理由很直接：「回放得慢一点」与「回放的根本不是这段时序」在结果里长得一样——一次被悄悄当成 1.0x 的 0.5x 回放，会让依赖节奏的下游测试通过，却验证了错误的条件。这类错误必须在入口处变成异常，而不是在结论里变成一个说不清的绿勾。

`timing` 为 `None`（旧格式 / 非流式响应）或空列表（流式但未采集到 chunk）时走瞬时回放：一次性产出完整响应文本、不 sleep，文本口径直接复用 `play()`，不给响应构造留第二份实现。偏差此时恒记 0.0——没有等待就没有等待偏差，把「构造响应对象花了多久」混进调度指标里只会污染它的含义。

## 【备选】放弃了什么，为什么

### 备选 A：`on_chunk` 回调函数式回放

**放弃。** 回调的表面成本更低（不用管迭代器状态），但它把「异常从哪一层抛出」「怎么提前中止」「谁持有产出缓冲」三个问题全部推给调用方自行解决。更实质的问题是它无法自然表达**拉取式节奏**：回调模式下调度器会一口气把所有片推给回调，而流式使用方需要的是「我准备好了就给我下一片」——两者的节奏由不同的一方掌握时，必须有一层缓冲去吸收错配，而缓冲放在哪、满了怎么办、谁来定策略，都会变成新的可配置项。生成器把节奏所有权交回消费方，这些问题根本不会出现。

### 备选 B：基于 asyncio 的精确时序回放（async generator）

**放弃（当前阶段）。** 这条路技术上更强：`asyncio.sleep` 不阻塞事件循环，且能挂上 deadline 做更精细的调度，与 ADR 0002 确立的并发形态天然契合。它没被选中，不是因为做得不好，而是因为**此刻的收益还不存在**：

1. `replay.py` 目前不处在任何事件循环里，引入 async 会强制所有调用方变成 async——包括那些只想同步读一个完整响应的适配器路径；
2. 同一进程内的「精确时序」并没有比 `time.sleep` 强多少：真正的精度上限来自操作系统定时器粒度（见边界一），不是来自同步还是异步；
3. 真实流式的调用方形态（httpx 的 `aiter_bytes` 等）要到适配器层落地时才确定（CLI 集成与流式对接在 M1-D12 及之后）。届时若发现同步生成器确实无法对接，改为 async 是一条清晰的升级路径——因为**调度逻辑与消费形态是分离的**，`_iter_timed_chunks` 只做「算出目标时刻、等到位、产出」，换成 `await asyncio.sleep` 不影响其余任何一层。

### 备选 C：给 `play()` 增加 `timed: bool = False` 开关

**放弃。** 见决策二。单入口少一个函数名，但把一个必须表态的选择变成了可省略的参数。真实事故形态是这样的：某个新调用点按 D6b 的既有印象写了 `play(cassette)`，读到的响应完全正常（一次性给全，断言全过），但依赖流式节奏的用例从未真正被验证——而报告上显示「通过」。这类失败不会在任何日志里留下痕迹，因为它不是失败，是**没测**。

### 备选 D：把偏差统计作为 `play_timed` 的返回值

**放弃。** 生成器无法在产出内容的同时再返回一个值：要么把统计塞进一个「最后一项」，要么让调用方先跑一遍再跑一遍（双倍等待，且第一次的调度会污染第二次的测量），要么在迭代结束时抛一个携带统计的异常。前两种污染了产出契约，第三种把正常结束变成了异常路径。

把统计挂在**流对象**上（决策四）同时避开了三者：迭代器的产出契约保持纯粹（只产文本），统计按需读取，不需要统计的一方零成本。

### 备选 E：逐片 sleep 间隔（朴素实现）

**放弃。** 见决策三。这是本 ADR 里最容易被写出来、也最容易被忽略的一版：它在短流上看不出问题，错误只在长流尾部才显形，而长流恰好是压测与稳定性用例最常出现的地方。

## 【边界】什么条件下这个决策失效，届时怎么办

**边界一：操作系统定时器粒度决定偏差下限。** `time.sleep` 只能保证「不早于」目标时刻，无法保证「准时」。Windows 的传统定时器粒度约 15.6ms，Linux 通常在 1ms 量级；实测本机（Windows 11 / Python 3.11）最大偏差不足 1ms，因为 Python 自 3.11 起在 Windows 上改用高精度等待，但这一保证依赖运行时实现，**在老环境或高负载 CI 上偏差可能达到十几毫秒**。因此测试断言一律采用宽松阈值（50ms），并且倍率相关的正确性断言**不依赖墙钟**——改用「sleep 收到的参数」与「计划到达时刻（纯算术，可精确断言）」两条确定性口径。**触发复审的条件**：若 CI 上出现无法用负载解释的时序不稳定，或需要验证的恰恰是「毫秒级延迟是否影响被测行为」，届时应把调度器换成 deadline 驱动的忙等（牺牲 CPU 换精度），并以独立开关提供，不改变默认路径。

**边界二：极大倍率退化为「不 sleep 但仍逐片产出」。** 倍率高到间隔小于定时器粒度时，继续 sleep 只是徒增系统调用，还可能因错过时间片反而睡过头，因此低于 1ms 的等待直接跳过。但**退化口径必须是逐片产出而不是一次性给全**：流式使用方（打字机、进度条）依赖 chunk 边界，把 4 片合并成 1 片会让下游拿到的结构整体变形。代价是此时实测偏差会等于被跳过的间隔（最大 1ms 量级），这是可解释的取舍而非缺陷。

**边界三：浮点精度只在两个确定的位置被收敛。** `arrival_ms` 在录制侧收敛到 3 位小数（微秒精度），偏差统计在读取侧同样收敛到 3 位小数——否则浮点尾差（如 `0.1+0.2`）会在报告里显示成刺眼的长尾小数。倍率折算全程用**除法**（`间隔 ÷ speed`）而非乘法，`speed` 必须是正有限数，这一约束同时挡住了负间隔与 NaN 两条崩溃/静默路径。

**边界四：`None` 与 `[]` 回放行为相同，语义不同。** 两者都走瞬时回放，但只有 `timing is None` 能断定「这是一次非流式响应（或旧格式 cassette）」，`timing == []` 表达的是「流式但未采集到 chunk」。判定逻辑刻意留在 `if not timing` 这一处，因为它对应的是「有没有时刻表可调度」这一唯一问题；至于为什么是这两种形态，语义归属在 D06b 的录制侧就已固定。**若将来出现第三种「有时序但不可调度」的形态**（例如 timing 被损坏成乱序），应在**契约层**拦住，而不是让调度层猜。

**边界五：时序回放不能替代真实 TTFT 测量。** 这条边界必须写在最显眼处：`play_timed()` 复现的是**录下来的节奏**，它证明的是「被测代码在给定节奏下的行为」，而不是「这段流真的能在 380ms 内吐完字」。任何以延迟为验收标准的指标（项目目标中的 TTFT 门禁、质量门禁阈值）都必须走真实调用；用回放节奏去论证一个延迟指标是否达标，是把测试工具变成了自证的闭环。触发复审的条件：M4 引入真实 TTFT 测量后，若出现「回放节奏被误当作性能基线」的实际案例，应在 CLI 与报告层显式区分「录制节奏」与「实测延迟」两类数字。

**复审时点**：M1 收口（M1-D12 CLI 集成）后复审一次，重点确认两件事——同步生成器能否直接对接适配器层的流式读取形态，以及是否需要在 CLI 侧暴露 `speed` 与偏差阈值。
