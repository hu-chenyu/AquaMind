# ADR 0007：报告以 jinja2 渲染为自包含单文件 HTML

- **日期**：2026-09-26
- **状态**：已接受（Accepted）
- **关联**：技术栈选型（见开发计划）、`docs/ROADMAP.md` 任务 M4-D09a/b
- **决策者**：hu-chenyu

---

## 【决策】我们选了什么

**评测结果为 jinja2 模板渲染生成一个自包含的单文件 HTML：样式内联、图表用内联 SVG 表达、不引用任何外部资源，一个文件双击即可离线打开。**

这条决策首先保障的是"报告能抵达它该去的地方"。LLM 评测的结果往往不是给跑命令的人自己看的，而是要发给同事、贴进项目周报、归档到某个版本目录里。如果它需要起一个服务、或者依赖 CDN 加载样式，那么在绝大多数办公场景里它就传不出去——接收者打开是一片空白。

其次它保障的是长期可读性。一份包含了完整数据渲染结果的 HTML 文件，在若干年后不需要任何运行环境即可打开；而一个在线看板则要求那个服务还活着。对一个会被归档、会被版本对比的工具来说，这是实质性的差别。

图表部分选择内联 SVG 而非图表库，是同一逻辑的延伸：引入外部 JS 图表库意味着要么引入 CDN 依赖（违反离线原则），要么把压缩后的 JS 内联进文件（体积膨胀且难以控制）。手写 SVG 虽然牺牲了一部分表达力，但换来的是完全可控的体积和离线可用性。

---

## 【备选】放弃了什么，为什么

### 备选 A：在线看板

**放弃。** 在线看板的交互能力最强，可以钻取到任意一条用例的细节，这也是评测类工具常见的形态。但它需要一个常驻服务，由此带来的部署、鉴权、数据存放等问题会立刻把我们拖回 ADR 0001 已经否决过的平台形态。

另一个容易被忽略的问题是"传不出去"。看板的链接通常是内网地址，脱离内网即失效。而本项目的核心人群需要在各种网络环境里分享结果，这一点上看板是结构性劣势。因此它只能作为**叠加层**出现在维护期（见边界条款），而不能作为默认产物。

### 备选 B：PDF

**放弃。** PDF 在流转性上与 HTML 单文件接近，且排版固定、适合打印。但生成 PDF 通常需要额外的渲染引擎（浏览器截图或排版库），这会引入重量级依赖，与"轻量一体化"的目标冲突。

可维护性是第二个问题。PDF 的内容调整依赖完整的重新渲染，模板迭代的反馈链路长；而 HTML 可以在浏览器里即时调试。此外 PDF 无法承载折叠区块、悬浮提示这类轻量交互，而这些能力在展示证据片段和长列表时很有用。

### 备选 C：只输出 JSON，配套独立前端

**放弃。** 这个方案的工程分工最清晰：Python 侧只负责产出数据，前端负责呈现。但它要求使用者具备一套前端工程环境（构建工具、依赖安装、本地服务），等于把"看结果"这件事的门槛提高到"先搭建前端"。

对本项目的使用者而言，他们想要的是跑完即得，而不是被迫维护两条技术栈。JSON 本身仍然会作为机器可读的产出格式保留（用于 CI 消费与二次处理），但它不是给人看的那一个产物。

## 【边界】什么条件下这个决策失效，届时怎么办

**触发条件一：使用者需要对结果做交互式钻取。** 当评测规模上升到数百条用例时，单文件 HTML 只能提供有限的筛选与折叠，深挖变得低效。届时退路是**在库之上叠加一个薄的本地 Web 层**，读取已有的评测结果目录做展示——注意这一步只是增加了一个可选视图，单文件 HTML 仍然继续产出。它属于 ADR 0001 边界条款中已预留的那条退路。

**触发条件二：文件体积失控。** 若单份报告需要容纳全部原始样本、完整对话轨迹与全部攻击用例，内联 SVG 与内联数据会让文件膨胀到难以通过邮件发送。届时的处理是在模板层引入"详略分级"：默认产出精简版用于流转，另存一份包含全量数据的扩展产物用于归档，而不是扭转"单文件优先"的默认。

**触发条件三：出现需要服务端能力的分析需求。** 例如跨版本趋势对比需要从多个历史报告中提取数据——这在单文件形态下要靠外部脚本完成。届时的做法是提供一个 `aquamind report` 的对比视图，而非引入服务；若确有强需求，则按 ADR 0001 的流程复审形态决策本身。

**复审时点**：v1.0 发布后（M6 收口 / 维护期首月）随文档三件套审计复审一次，重点确认体积阈值与是否需要引入详略分级。
