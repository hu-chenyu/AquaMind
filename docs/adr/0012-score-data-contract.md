# ADR 0012：评分输出契约 Score / ScoreTrace——归一化分数、产出即终态、追溯链终值即最终分

- **日期**：2026-10-17
- **状态**：已接受（Accepted）
- **关联**：M2-D01（Day19 数据契约）、ADR 0004（pydantic v2 选型）、输入侧契约 `models/testcase.py`；
 消费方：M2-D03 精确匹配、M2-D05 rubric、M2-D06/D10 聚合、M2-D07 Judge 适配器、M2-D12 分数落库
- **决策者**：hu-chenyu

## 【决策】我们选了什么

**评分链路的输出侧由三个严格 pydantic v2 模型承载：`Score`（单条评分结果）+
`ScoreStep`（链上一步）+ `ScoreTrace`（追溯链路）；分数一律归一化到闭区间 0.0-1.0；
三个模型全部 `frozen=True` 且 `extra="forbid"`；`ScoreTrace.final_score` 恒等于链尾步骤的
`partial_score`；时间戳必须带时区。**

### 决策一：用 pydantic v2 严格模型，而不是 dataclass / TypedDict / 裸 dict

输入侧契约（`TestCase` / `ExpectedSpec` / `ScoreTag`）已经是 pydantic v2 严格模型，输出侧
与它同构有两个直接收益：其一，**坏数据在边界处被拦住**——`extra="forbid"` 让拼错的字段名当场
报错，而不是静默丢弃后产出一个"看起来正常"的分数；其二，**契约即文档**，字段约束写在类型上
（`ge`/`le`/`min_length`/`AwareDatetime`），评审与下游实现读同一份定义，不需要另写一份校验代码。

反过来的代价（模型层抽象）在 M2 这种"输出要被落库、被聚合、被报告消费"的场景里是净收益：
分数产物几乎每次使用都要经 JSON 落盘与回读，`model_dump_json` / `model_validate_json` 的
往返无损是**契约自带的能力**，而 dataclass 与 TypedDict 都需要各自再写一层序列化。

### 决策二：分数一律归一化到 0.0-1.0

不同评分器的原生尺度各不相同（精确匹配是 0/1，rubric 是加权字段分，Judge 常给 1-5 分）。
如果契约允许"各自的原生尺度"，那么聚合（M2-D06/D10）、阈值比较、跨运行对比全部要在
"这条分数是什么尺度"上做隐式假设——而这类假设一旦错了，产出的数字仍然合法，只是含义错了，
且没有任何报错。归一化到 0.0-1.0 把这些假设**移进契约**：入契约即同一尺度，尺度转换是
各评分器自己的责任（转换点可被单测固定）。

`allow_inf_nan=False` 与输入侧 `TestCase.weights` 同口径：NaN 与任何数比较都为 False，
`ge`/`le` 都拦不住它，但它会让加权聚合整体变成 NaN，且 JSON 序列化后是 `null`——
"构造成功 → dump → validate"这条自洽往返会当场断掉，而追溯链一旦无法往返，就失去证据价值。

### 决策三：产出即终态——`frozen=True`

评分结果生成后不应被就地改写。可变的害处不是"有人会恶意改分"，而是"**一次顺手修正就会让
报告与证据分叉**"：比如某处判断"分数太低了，调到 0.9 更好看"，于是 `Score.score` 变成 0.9，
而 `ScoreTrace` 里链尾仍是 0.5——两个数字各自都合法，没有任何报错，只有人工逐条核对才能
发现。要改结论的正确做法是重新评分、产出一个新的 `Score`，让新结论与新的追溯链同时出现。

需要区分 `frozen=True` 与 `validate_assignment=True`：后者只保证"赋值也要过校验"，
数值仍然可以改（0.5 → 0.9 完全合法）；契约要的是"不可改"，所以取 `frozen=True`。
这与输入侧契约的取向不同是有意的——`TestCase` 在批量执行器里可能被逐步填充，而评分产物
是在评分器返回那一刻就已完备的终态对象。

**但 `frozen` 不是全部（D19 复核对齐修补记）**：pydantic v2 的 `model_copy(update=...)`
默认**不跑任何校验**，于是 `score.model_copy(update={"score": 5.0})` 能一行造出越界分数的
副本、`trace.model_copy(update={"final_score": 0.9})` 能绕过追溯链不变式——决策三要防的分叉
可以从官方 API 直接进来。因此三个模型都重写了 `model_copy`：不带 `update` 时保持官方语义
（纯复制，不做无谓重校验），带 `update` 时把 `update` 的**原样取值**并回字段值再走
`model_validate`，与直接构造同一条校验路径。**"并回原样取值"这一步不可省**：`model_copy`
自己会静默丢弃「不属于本模型」的键，若只对副本重新校验，`extra="forbid"` 就形同虚设
（拼错的字段名被吞掉，与契约口径相悖）。

### 决策四：追溯链的结构——`steps` 非空、终值即最终分、时间戳带时区

- **`steps` 至少一步**（`min_length=1`）：没有步骤的追溯链解释不了分数从何而来；
- **`final_score` 必须等于链尾的 `partial_score`**（`model_validator(mode="after")`）：
 把"结论"与"证据"焊死。多评分器聚合（M2-D06/D10）也遵守这条——**聚合动作本身就是链上的
 一个显式步骤**，其 `partial_score` 即聚合结果。允许 `final_score` 与链尾脱钩，等于允许
 结论与证据各说各话，那正是本契约要防的事。
 **取值纪律（精确相等的前提）**：这条比较是**精确相等**而非容差比较，因此两处取值必须
 来自**同一计算结果**——写成 `final_score=steps[-1].partial_score`，或从 `Score` 侧写成
 `final_score=score.score`；**禁止分别计算后各自填入**（两次独立计算即使公式相同，也可能
 因浮点运算顺序差异得到不等的值，从而把一个正确实现误判成契约错误）；
- **时间戳用 `AwareDatetime` 且不给默认值**：naive datetime 在跨时区比对时会静默错位；
 不给默认值是为了避免在测试与复算链里冒出"看似相等实则不同源"的隐式当前时间——
 时间必须由调用方显式给出。

### 决策五：`scorer` 用受限字符串，不用 `Literal` 枚举

输入侧 `ExpectedSpec.type` 用 `Literal` 是对的：`type` 决定 `value` 的解释方式，取值集合必须
封闭，拼错会一路飘到打分器并静默产出错误分数。输出侧 `Score.scorer` 不同：M2-D11 的评分器
注册机制是**运行时注册**，且 Judge 类标识会带模型名后缀（`judge-gpt-4o-mini`），
用 `Literal` 会把扩展权限锁死在契约层，每加一个评分器都要改契约。因此取"非空字符串 +
与 `ExpectedType` 对齐或扩展"的约定，靠注册机制（D11）而非类型系统兜底未知标识。

### 决策六：`metadata` 作为显式的扩展口袋

评分器总有个性化信息要带（Judge 的采样次数、原始终端输出摘要、降级来源等）。
若不给出口，各评分器会各自想办法往固定字段里塞，最终让固定字段的含义随评分器而变。
`extra="forbid"` 管的是"未知的**顶层**字段"，与"已知字段承载自由内容"不冲突：
`metadata: dict[str, Any]` 明确划出一条"约定之外的附加信息"通道，固定字段则保持语义稳定。

## 【备选】放弃了什么，为什么

### 备选 A：`@dataclass(frozen=True)` 定义三个契约

**放弃。** dataclass 的 `frozen` 只挡属性赋值，不提供任何**校验**：分数越界、空理由、
缺时区都要自己写 `__post_init__`，而每个模型都要重复一遍这些检查；嵌套的 `ScoreStep`
不会自动校验（`steps: list[ScoreStep]` 里的 dict 不会被转成 `ScoreStep`）；JSON 往返要
自己写 `to_dict`/`from_dict`。最终会得到一个"手写的、残缺的 pydantic"。

### 备选 B：`TypedDict` + 运行时校验函数

**放弃。** `TypedDict` 只在静态检查期存在，运行时就是个普通 dict：`Score(**payload)`
不会因为字段拼错而报错，也不会把越界分数拦下来——**类型标注在运行时是空操作**。
本项目的核心口径是"坏数据在边界处被拦住"，而 `TypedDict` 恰好不提供运行时边界。

### 备选 C：直接传裸 dict（约定俗成的键名）

**放弃。** 键名靠约定即意味着三条链路（评分器 → 落库 → 报告）各写一遍 `payload["score"]`，
任何一处拼错都在运行时变成 `KeyError` 或静默的 `None`，且没有字段定位信息。更关键的是
**约束无处安放**：分数范围、理由非空、时间戳时区这些不变量会散落在各消费方的 `if` 里，
每个消费方漏一条就少一条。

### 备选 D：分数用 0-100 整数尺度

**放弃。** 0-100 看似"更符合直觉"，但它与 0-1 相比没有任何表达能力增益（都是归一化尺度），
却引入了新的分歧面：小数位怎么算、100 与 1.0 混用时谁是谁、聚合后的分数要不要四舍五入。
0.0-1.0 是概率与比率的自然尺度，跨评分器比较、阈值设定、效应量计算（M4 的 S3）都在这个
尺度上直接可用，不需要额外的单位换算。

### 备选 E：可变模型 + `validate_assignment=True`

**放弃。** 见决策三：`validate_assignment` 保证的是"赋值也合法"，不是"不可改"。
0.5 改成 0.9 是合法赋值，但会让报告与追溯链分叉——契约要拦的正是这一种。

### 备选 F：允许 `final_score` 与链尾脱钩（链只作参考）

**放弃。** "链是参考、结论独立"听起来更灵活，实际是把**最需要被机器检查的一致性**降级为
人工检查。追溯链的价值全在"结论可从链复算"：若终值可以独立设置，那么一份分数与一份看起来
很详尽的链路可以彼此矛盾而不被发现，报告的证据力反而比"只有一个数字"更差——因为它假装
有证据。聚合场景由"聚合作为显式步骤"覆盖（决策四），没有必须脱钩的真实需求。

### 备选 G：步骤用 `tuple` 而非 `list`，把不可变做到底

**放弃（保留为后续会话的候选）。** `tuple` 能把 `steps` 的**内部**也冻住
（`frozen=True` 只挡属性重绑定，不挡 `trace.steps.append(...)`）。放弃的理由是契约可读性：
`list` 是绝大多数人对"步骤序列"的直觉写法，且 `model_dump_json` 后两者都是 JSON 数组。
本契约把 `ScoreTrace` 定位为"评分器返回后即不再触碰的终态对象"，调用方在构造前持有列表、
构造后不再改——**这条纪律写进文档并由 M2-D06/D10 的聚合实现共同遵守**；
若 M3 出现真实的"链被就地追加"事故，再切 `tuple`（属契约收严，需新开 ADR）。

## 【边界】什么条件下这个决策失效，届时怎么办

**边界一：本契约只定义输出模型，不含任何评分逻辑。** `Score` / `ScoreTrace` 回答的是
"分数长什么样、证据长什么样"，不回答"怎么打分"。精确匹配（M2-D03）、rubric（M2-D05）、
Judge（M2-D07）各自实现打分并构造本模块的模型；**本日不实现、也不预埋任何打分函数**。
**触发复审的条件**：若某个评分器发现契约无法表达它的输出（例如需要多终点分数），
应当是"扩展契约"（新字段 + 新 ADR）而不是在评分器里另起一套输出结构。

**边界二：Judge 适配器的结构化输出在 M2-D07 消费本模型。** D07 的职责是把裁判的
结构化 JSON 解析成 `Score` + `ScoreTrace`，解析失败降级为不可判（UNJUDGEABLE，M2-D08）——
降级路径的表示方式（是 `passed=False` + `metadata` 标记，还是另开一个评分结果类型）**留待
D07/D08 决定**，本契约不预设。**触发复审的条件**：若 D08 的降级语义无法用 `Score` 表达且
不适合塞进 `metadata`，应新开 ADR 讨论"不可判"是否需要一个独立结果类型（而不是把
「不可判」硬塞进 `passed: bool`）。

**边界三：多评分器聚合在 M2-D06/D10 处理，本契约只提供结构。** 字段级权重、归一化口径、
缺失字段策略都由 D05/D06 决定；本契约唯一的要求是"聚合结果必须作为链尾步骤显式登记"
（决策四）。**触发复审的条件**：若 D06 的聚合需要"部分评分器缺席"这类结构性信息，
优先考虑用 `metadata` 承载（它是为此预留的口袋）；若最后发现 `metadata` 被多个评分器
抢用、含义开始不稳定，则说明该信息值得升格为固定字段，届时应改契约并新增 ADR。

**边界四：`case_id` 的来源不在本契约内。** 当前输入侧 `TestCase` 没有唯一标识字段
（M1 的用例契约只有 `input` / `context` / `expected` / `score_tags` / `weights`）。
因此 `case_id` 在 D19 只能由调用方给出；M2-D02（测试集格式 jsonl/yaml + 校验器）落定后，
由加载器提供稳定的用例标识，D12 分数落库时以它作为关联键。**触发复审的条件**：若 D02 的
用例标识形态与 `str` 不兼容（例如需要复合主键），应在 D02/D12 一并调整本字段类型，
而不是在落库层做字符串拼接。

**边界五：`passed` 与 `score` 之间没有数值绑定。** 通过与否由评分器按自身阈值判定
（精确匹配是"全中才算通过"，rubric 可能按阈值，Judge 的通过取决于结构化字段是否完整），
契约不强制 `passed ⇔ score ≥ 某常数`——一旦写死这个等价关系，不同评分器就失去了各自的
通过口径。**代价**：存在"score=0.8 但 passed=False（缺必填字段）"这类看起来别扭的合法组合。
**触发复审的条件**：若 M2-D06 聚合或 M4 报告需要"全局通过线"，该阈值应作为**分析层参数**
（预注册冻结的一部分）而不是契约层不变量。

**边界六：`frozen=True` 冻结的是属性重绑定，不是容器内容。** `Score.matched_tags`、
`Score.metadata` 与 `ScoreTrace.steps` 都是可变容器，`trace.steps.append(step)` 不会被拦下
（备选 G 记录了切 `tuple` 的候选）。这条边界在 D19 复核对齐后**只剩容器内容这一个口子**：
`model_copy(update=...)` 那条"官方后门"已由决策三的 `model_copy` 重写收口，`frozen` 与
`model_validate` 两条路径都不再可绕。**触发复审的条件**：出现真实的"链被就地追加/篡改"
事故即切 `tuple`；在此之前靠"构造后不再触碰"的纪律与本 ADR 留痕。

**边界七：JSON 往返的"无损"以模型相等为准，不是字节相等。** `timestamp` 落盘为
`2026-10-17T09:00:00Z`、回读后是 UTC 感知的 `datetime`，`+00:00` 与 `Z` 两种写法在
模型层相等但字节层不同；浮点分数字段同理（`0.5` 往返恒等，但跨语言实现的格式化可能不同）。
**触发复审的条件**：M5 的"双跑逐字节一致"验收作用于**同一实现**的两次运行，不适用于
跨语言/跨版本比对；若将来需要跨实现比对产物，应改成"模型相等 + 显式归一化后比对"，
而不是直接比字节。

**边界八：`Score` 与 `ScoreTrace` 的跨模型一致性不由契约强制（D19 复核留痕）。** 不变式
只焊在 `ScoreTrace` **内部**（`final_score` = 链尾 `partial_score`），而 `Score.score` 与
`ScoreTrace.final_score` 分属两个**互不引用**的模型：`Score(score=0.5)` 与一条
`final_score=1.0`、内部自洽的链路可以各自合法地成对出现，契约层拦不住——这正是决策三
要防的那类"结论与证据分叉"，只是分叉点从"一个模型内部"移到了"两个模型之间"。因此本契约
的口径是**成对构造**：`final_score` 应直接取 `score.score`（`scripts/score_contract_example.py`
与 `examples/score_contract/demo.py` 都已示范 `final_score=score.score` 这一写法），两份产物
在同一处产生，不分别计算后再填。**M2-D06/D10 的聚合实现必须提供成对构造的工厂函数**
（一次调用同时产出 `Score` 与 `ScoreTrace`），禁止分别构造后各自独立修改。
**触发复审的条件**：D12 分数落库或 M4 报告消费分数时，若出现真实的"Score 与 Trace 不配对"
事故，应把配对关系升格为**运行时校验**（例如落库前比对 `final_score == score.score`，
不一致按数据错误拒绝入库），而不是继续依赖构造纪律。
